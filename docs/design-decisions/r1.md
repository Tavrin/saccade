2. Every new answer from decide, a session or a judge panel is a proposal.
   Source labels (including `human`), confidence, calibration and panel agreement
   cannot assign a final decision. The empty historical `[decisions]` table can
   still parse; its removed promotion settings are rejected. Historical finals
   and their promotion flags remain readable, but cannot authorize an update.
   Blind ties remain unresolved instead of becoming acceptance proposals or
   candidate-acceptance labels.
3. Approval uses two steps with the existing command: `--report REPORT --dry-run
   --out PLAN` prepares the selected manifest, case and canonical CLI decision
   draft; `--report REPORT --decisions PLAN/decision.json --out RECEIPT` consumes
   the explicitly reviewed disposition. `--entry NAME` selects a subset;
   `--all-failing`
   selects failing/new entries for preparation. Applying cannot expand the
   decision's scope. The draft is unattested and is not an approval receipt.
   No report-only, positional-only or legacy-final application is allowed.
4. The decision binds the R4 canonical case, selected input hashes, scope and
   exact reviewed artifact. The case references the authoritative report and
   effective settings without duplicating metrics. Repeatable `--entry` avoids
   ambiguity between entry names and optional positional directories. Present
   image sidecars also
   participate in identity. All reviewed baseline and candidate contents,
   including their absence, are checked before updates; report and sidecar
   changes fail closed. Deletions need both `approve_deletions: true` in the
   accepting decision and `--prune-missing`. Force overrides are removed.
5. CLI application writes canonical case/decision/receipt records, the manifest
   and a `.saccade-run` marker outside capture inputs. Receipts always use
   `channel: cli` and `human_attestation: null`. Input bytes are staged before
   application. Atomic file replacement avoids truncating an individual baseline;
   the operation is not a multi-file filesystem transaction against concurrent
   external writers. An I/O failure after an earlier replacement can leave a
   partial update, but cannot produce a valid complete receipt. This boundary does
   not establish hostile-shell authentication or live-session verification.
6. Owner-approved addition: decision authority has three distinct levels:
   `human` (a workbench-attested receipt), `cli` (unattested), and RESERVED
   `automated` (policy ID plus exact evidence case digest). The read-only canonical
   `automated_decision` variant carries `authority: {level: automated, policy_id,
   evidence_digest}` and its exact review binding. It is not a HumanDecision.
   Readers and summary display it as `automated`; human-required checks reject
   it regardless of disposition. Supported bundle writers, approve, and MCP
   cannot issue or apply it. P5 may add policy-gated issuance after release.
   A workbench decision without an attested receipt remains unattested.
7. Agent entry packs derive from `integrations/agent-guide.md` and stay below
   roughly 1,200 tokens. They require explicit human authorization, describe
   exposure and the shell trust boundary, and never allow calibrated approval.
