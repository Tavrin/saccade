# R12 transport-fix decisions

Binding sources: `SPEC-r12-transport-fix.md` and `DESIGN-1.0.md` §9 as amended by §16. The corpus, splits, rubrics, truth and job plan stay frozen (`moss-pilot.toml`, `sha256:1d2b0d4d…`). Everything below is a decision taken without the owner; each states the rejected alternative and its reversal cost.

## Root cause of the Jev HTTP 400s

- **Finding.** Jev rejects oversized requests with `400 {"detail":{"error_type":"max_tokens_exceeded"}}`. This is an input-token limit. The 14 refusals in the partial run were all batches whose encoded payload was 62,229–88,983 bytes. Every successful batch was at most 64,235 bytes; the bands overlap because the limit counts tokens, not bytes. Field names, schema and encoding were identical in failing and successful requests. Only the size differed.
- **Evidence.** The R11 boundary discarded error bodies, so the cause was not recorded. I replayed the smallest refused payload once through the fixed boundary. That consumed one Jev attempt, counted inside the 288 remaining. The retained body named the error type.
- **Second defect.** The R11 example finished every non-2xx response as `unavailable`. That started the shared `jev/jev-latest` probe cooldown, and all later Jev jobs were deferred behind one oversized request. The 56 zero-attempt Jev "deferred" exchanges in the partial run came from this.
- **Fix (encoder).** `corpus_live.jev_chunks` halves a case's question batch while its encoded payload exceeds 60,000 bytes. It also halves a batch after a `max_tokens_exceeded` refusal. Each question's request object, instruction text and criteria are byte-identical to the frozen encoding; only which questions share one HTTP request changes. Completed batches survive resumes, keyed by a digest of the requests. *Rejected:* deduplicating the shared evidence across questions inside one payload. That would change the encoding of every Jev request and mix two encodings in one evaluation. *Reversal:* cheap while unmerged.
- **Fix (transport/ledger).** HTTP 400/413/422 are recorded with the new ledger outcome `rejected`. The attempt stays consumed, but no probe cooldown starts and the provider is never stopped. 401/403 stop the provider. Any other 4xx, such as a missing model, marks only that model unavailable. Production `execute` previously stopped the provider on any non-transient status, a 404 included; it now follows the same rule. *Reversal:* cheap.
- **Regression tests.** `jev_token_limit_refusal_is_rejected_without_cooling_the_provider` (Rust, using the recorded response body) and `test_jev_token_limit_batches_split_without_changing_question_requests` (Python). The Python test uses a synthetic 62–66 KB payload with the recorded request shape; it contains no key and no private data.

## Gemini pacing and backoff

- **Pacing** is user-level only: `[pacing."gemini"]` or `[pacing."gemini/<model>"]` in `~/.config/saccade/user.toml`, with `requests_per_minute` and `concurrency`. A model entry can only narrow the provider entry. Project files cannot set pacing, because `ProjectPolicy` rejects unknown fields. The defaults are conservative: Gemini allows 6 requests per minute and 1 in flight, provider-wide across every fallback model; Jev allows 20 per minute and 2 in flight; other providers allow 10 and 1.
- **Enforcement.** Pacing is enforced inside the locked ledger transaction (`Ledger::reserve_paced`). Concurrent processes therefore cannot jointly exceed it, and it can never add attempts beyond the budget caps. A paced refusal consumes nothing. The transport waits for it within its timeout; a longer wait returns `deferred retry_at=<ms>` without any dispatch. Crashed reservations hold a concurrency slot only for the request timeout plus 30 s, but stay consumed for budget purposes. *Rejected:* a per-process token bucket, because it would not hold across the corpus's one-process-per-attempt transport or across MCP and CLI.
- **Provider waits.** The `Retry-After` header is honoured. When it is absent, the structured Gemini `google.rpc.RetryInfo.retryDelay` in the error body is honoured, rounded up.
- **Backoff.** 429, 5xx and transport failures retry the same model up to twice before any fallback. The wait starts at 1 s, doubles per retry, adds up to 50% random jitter, and is never shorter than the provider wait. A wait beyond the deadline defers that model and records the provider's `retry_at` in the shared probe state. The corpus transport now calls `execute_observed` on one model with a 240 s deadline. The scheduler alone decides fallback to the next chain model, and pinned jobs never substitute. Same-model retries are allowed for pinned jobs, because a retry is not a substitution.
- **Availability** is still recorded per model separately from accuracy. Failure categories are now counted per HTTP attempt as `status + provider error class`.

## Resuming without re-freezing

- `examples/evaluation/resume-amendment.json` is bound to the frozen manifest hash. It replaces only the transport adapter and executable identities, and opens a new 3-hour elapsed window: the original 1-hour window had already passed. `corpus.validate` accepts an amended identity only for those five files and the `transport` executable. Cases, splits, rubrics, truth and the job plan are still checked against the frozen manifest.
- The amendment is a deviation from a strict single-window §9 run, and it is published. *Rejected:* re-freezing, which the spec forbids, and leaving the window closed, which would leave 311 jobs unattempted for a client fault. *Reversal:* load-bearing for the published numbers once committed.
- The resume reopens every unresolved provider job once (epoch `r12-transport-fix/1`) on a fresh retry schedule. Answered and invalid results are never replayed.
- The caps for this run are the totals minus the partial run's usage: Jev 288 and Gemini 133. The ledger scope still enforces 400/250 in total, which is the same constraint.

- **Scheduler exit fix.** After the dispatch work, every remaining retry was scheduled after the window ended: Gemini's daily-quota delay is about 84,800 s. The scheduler would still have slept until the window closed. I stopped the run by its pid and added one loop exit: stop waiting when every pending retry falls after the window. I then re-recorded the amendment, so `corpus_live.py`'s published hash is the final code, and re-ran it to apply the existing post-steps and scoring. That fix does not touch the dispatch path, and the re-run made no provider calls (the ledger totals were unchanged at Jev 151 and Gemini 122). *Reversal:* free.

## Gemini outcome

Retained error bodies show that the 429s are `GenerateRequestsPerDayPerProjectPerModel-FreeTier`, with a quota of 20 requests per model per day and a `RetryInfo` delay of about 23.5 hours. Client pacing cannot recover a daily quota. The transport records the provider's delay and stops spending attempts. The remaining Gemini jobs, and the Jev enriched jobs that depend on their observations, are reported as the exact remainder. Raising the quota means a paid tier, which is spending and stays a human decision.
