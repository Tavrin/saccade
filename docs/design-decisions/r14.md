# R14 Action and example workflows

1. Binary installation is the default. Missing assets/checksums, mismatches,
   unsupported release targets and unusable executables are installation errors
   (exit 2), with no source fallback. Explicit source mode uses the action
   checkout by default or the supplied git revision with `--locked`. Release
   asset names/targets match the existing release workflow; R15 owns packaging.
2. The immutable update manifest is R1's existing `approve --dry-run` plan,
   accompanied by its canonical `decision.json`. Trusted dispatch supplies the
   SHA-256 of the exact reviewed manifest bytes. No new evidence schema or
   approval authority is introduced. The original report is restored, never
   regenerated. R1 validates report, case, input/sidecar hashes, decision scope
   and deletion authorization; a dry-run must equal the pinned manifest before
   applying its selected entries. Every selected entry is staged, independent
   of the CLI's five-path summary limit. CLI receipts remain unattested.
3. “Trusted dispatch” means `workflow_dispatch` on the repository's default
   branch, with explicit write permissions. Both the workflow and the Action's
   write boundary enforce it. The update example downloads a supplied run and
   immutable artifact ID into temporary storage, then copies only three data
   trees. It never selects mutable latest evidence or executes downloaded code.
   A changed current baseline requires a fresh comparison and review. Tracked
   checkout changes or staged changes are rejected; consumers should keep
   generated captures outside tracked files.
4. `report-dir` is the original report bundle in update mode and a fresh output
   directory in comparison mode. A stale report cannot be uploaded as new
   evidence. JUnit and the hidden `.saccade-run` marker travel with failed
   reports. Job summaries are the default; comments are opt-in and same-repo
   only. Fork comparisons use read permission, no persisted credentials and no
   AI/provider keys. Outputs distinguish completed gates (`pass`/`fail`, 0/1)
   from installation/configuration/export/upload/update errors
   (`command-error`, 2). A successful update retains the original comparison
   verdict; the PR still needs review and is never automatically merged.
5. The Action uses the official default feature set; `prechecks` is required
   for the photosensitivity showcase. Shell paths use physical-directory
   resolution; Rust path assertions use the canonical helper and `/` spelling.
6. Installation, archive extraction and GitHub writes are mocked by contract
   tests. Comparisons, JUnit exports, dry-runs and selected updates use the CLI
   in temporary directories. Native installation and live fork/update behaviour
   require separate release qualification.
